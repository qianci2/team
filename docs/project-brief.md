# 最终项目任务书（团队执行版）

> 本文件把课程最终项目要求转写为团队可执行的规则；如与课程通知冲突，以课程通知为准。

## 1. 提交目标

- **提交仓库**：<https://github.com/qianci2/team>
- **评分重点**：提交历史与协作过程，而不是单次代码量或代码的“华丽程度”。
- **过程要求**：
  - 按阶段/功能拆分提交，禁止一次性上传全部内容；
  - 每个提交聚焦一个明确的改动点，提交信息说明目的与结果；
  - 使用 Conventional Commits（`feat:`、`fix:`、`docs:`、`test:`、`ci:` 等）；
  - 三人都有持续提交，且能看出各自的负责模块。

## 3. 协作模型

- 分支：`main`（发布）、`develop`（集成）、`feature/<模块>-<缩写>`、`fix/<主题>-<缩写>`、`docs/<主题>-<缩写>`、`chore/<主题>-<缩写>`。
- PR：功能分支 → `develop`，至少 1 人评审、CI 通过；作者不能自批。
- 合并：使用 merge commit（`--no-ff`），**不使用 squash**，保留每个人的提交。
- 发布：阶段结束 `develop` → `main` 的 release PR，更新 `CHANGELOG.md` 并打 tag。
- 节奏：每人每周至少 2–3 次提交，贯穿整个项目周期；不允许最后一周集中补。
- 身份：每个人使用自己的 GitHub 账号提交；不代提交、不伪造贡献。

详细规则见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

## 4. 交付物

1. 可运行的网页游戏（浏览器直接打开，或经静态服务器访问）；
2. 源码、单元测试、端到端/验收记录；
3. 需求与设计基线、README、路线图、测试报告、演示材料；
4. 完整体现三人分工的提交历史、分支与 PR 记录。

## 5. 范围与边界

- 沿用实验一需求 v2.1 与实验二设计 v1.0，需求编号与语义不改；确需修改时按 K-xx 记录。
- 服务端排行榜只交付**接口契约、客户端、降级方案与 mock server**，不实现真实后端（与设计基线一致）。
- 旧原型只作行为参考与测试用例来源，不整段复制，不进入主线历史。
- 不引入与选题规模不匹配的重型框架；运行时依赖需在 PR 中说明理由。

## 6. 验收方式

- `npm run check` 与 `npm test` 在干净环境可复现；
- 高优先级需求（FR/NFR/BR）能在代码、测试与追溯矩阵中定位；
- 三人贡献分布可见，提交时间分散在项目周期内；
- README 的快速开始步骤无需口头补充即可执行；
- 最终 tag `v1.0.0` 对应一个可演示、可回归的版本。
