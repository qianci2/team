## 3. 架构设计

**承接需求：** FR-01~FR-32（全部功能需求）、NFR-09（架构约束）、NFR-10（配置驱动）、G2/G4。

### 3.1 架构总览

本产品是"单机玩法为主、排行榜为可选增强"的轻量网页游戏，架构取**三层单向依赖 + 可选后端**的形态：前端是一个纯静态单页应用，内部按表现层、应用层、领域层三层划分，依赖方向自上而下单向不可逆；后端（排行榜服务）是可选组件，前端的排行榜模块通过一个接口适配器访问它，后端缺失时降级为本地模拟榜单，前端其余部分完全不受影响。

```text
┌──────────────────────────────────────────────────────────────────────────┐
│  浏览器（唯一必需运行环境）                                                │
│                                                                          │
│  ┌── 表现层（§3.2.1） ─────────────────────────────────────────────────┐ │
│  │  M6 渲染与动画   M7 音频与视效   M8 输入与输入队列                    │ │
│  │         │              │              │                              │ │
│  │         └──── 只读消费 ViewState ──┬── 只产出语义化输入事件 ──────────┘ │
│  └────────────────────────────────────┼───────────────────────────────────┘
│                                       │
│  ┌── 应用层（§3.2.2） ────────────────▼───────────────────────────────┐ │
│  │  M5 会话与场景控制（场景状态机、流程编排、弹窗、时钟）                │ │
│  │  M9 排行榜客户端（远端 / 本地模拟双策略）                            │ │
│  │  M10 存档与状态仓库（内存唯一事实源 + localStorage 适配器）           │ │
│  └────────────────────────────────────┬───────────────────────────────┘ │
│                                       │ 调用纯函数 / 读写快照             │
│  ┌── 领域层（§3.2.3） ────────────────▼───────────────────────────────┐ │
│  │  M1 棋盘核心引擎   M2 计分系统   M3 关卡流程引擎                    │ │
│  │  M4 经济与进度系统（星级 / 解锁 / 金币 / 生命 / 道具库存）            │ │
│  └────────────────────────────────────────────────────────────────────┘ │
│                                       ▲                                  │
│  ┌── 静态配置 ────────────────────────┴───────────────────────────────┐ │
│  │  DS-2 levels.json（构建产物）  内置默认配置（回落用）                 │ │
│  └────────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────┬───────────────────────────────────────┘
                                   │  HTTPS + JSON（可选，仅排行榜）
                    ┌──────────────▼──────────────┐
                    │ 排行榜服务（Node.js+SQLite）  │
                    │  HTTP-1 / HTTP-2 两个接口     │
                    └──────────────────────────────┘
```

架构的"规模匹配"判断：本产品是单人、单场景、无账号、无实时协作的休闲游戏，**不引入**框架、状态管理库、依赖注入容器、微前端或服务端渲染（理由见 §10 D-01/D-12）；整个前端按模块划分后共 12 个模块，其中 4 个纯逻辑模块（M1~M4）不依赖任何浏览器 API，因此可以在 Node 环境下直接跑单元测试与代理求解器（§12.1）。

### 3.2 分层职责与依赖方向

#### 3.2.1 表现层

| 层 | 模块 | 职责 | 允许依赖 |
| -- | ---- | ---- | -------- |
| 表现层 | M6 渲染与动画 | 把 `ViewState` 画成画面：棋盘、HUD、弹窗、粒子与补间动画 | M6 定义的类型、平台 API（Canvas 2D、rAF、定时器） |
| 表现层 | M7 音频与视效 | Web Audio 合成音效与背景音乐、静音、Page Visibility 暂停 | 平台 API |
| 表现层 | M8 输入与输入队列 | 鼠标 / 触屏 / 键盘 → 语义化输入事件；动画期间排队 | M6 布局信息（只读） |

表现层**不得**修改领域状态：它只读应用层提供的不可变视图快照，并且只向应用层提交语义化输入事件（`InputIntent`）。这条约束使 FR-25 的"动画期间输入排队"有确定落点：排队发生在 M8 的队列中，而不是散落于各处的回调里。

#### 3.2.2 应用层

| 层 | 模块 | 职责 | 允许依赖 |
| -- | ---- | ---- | -------- |
| 应用层 | M5 会话与场景控制 | 场景状态机（主菜单/选关/对局/排行榜/设置）、流程编排、弹窗、时钟与懒恢复触发 | 领域层全部、M10、M6/M7/M8 的接口 |
| 应用层 | M9 排行榜客户端 | 提交 / 查询、超时与降级、本地模拟榜单、提交状态机 | M10、网络 API |
| 应用层 | M10 存档与状态仓库 | 内存中的唯一事实源、订阅通知、localStorage 适配、迁移与合并 | 领域层类型、localStorage |

应用层是唯一的"流程编排者"：任何跨模块的编排（如"结算 → 写盘 → 刷新金币 → 播放音效"）只出现在 M5，领域层模块之间不互相调用、不感知彼此（M3 通过构造参数拿到 M4 的纯函数引用）。

#### 3.2.3 领域层

| 层 | 模块 | 职责 | 允许依赖 |
| -- | ---- | ---- | -------- |
| 领域层 | M1 棋盘核心引擎 | 棋盘生成、交换、消除、下落、补充、连锁、特殊元素、死局检测与洗牌 | M2（只读调用 `scoreEvent` 产出每步得分明细，不判定关卡目标） |
| 领域层 | M2 计分系统 | 得分构成、连锁系数、上限校验 | 无 |
| 领域层 | M3 关卡流程引擎 | 一次对局的运行时状态机与目标进度判定、失败/结算判定 | 只读引入 M1/M2 的纯函数 |
| 领域层 | M4 经济与进度系统 | 星级判定、解锁、金币结算口径、生命值、道具库存 | 无（星级判定在 M4 内实现，见 K-06） |

### 3.4 依赖关系与架构约束

依赖方向为 M6/M7/M8 → M5 → M10 → M4 → M3 → M2/M1，反向依赖一律禁止；`M1~M4` 之间只存在"数据依赖"（构造参数与返回值），不存在"控制依赖"（互不调用对方的流程）。领域层 import 图固定为 `M3 → M1 → M2` 与 `M3 → M2`，`M4`、`M11` 不 import 其他领域模块；该图无环（K-06）。据此立 5 条架构约束，作为实现与评审的检查单：

| AC-A1 | 领域层（M1~M4）不出现 `document` / `window` / `localStorage` / `Audio` / `fetch` / `Date.now()` 的直接使用（时间以参数注入） | 源码静态检索（正则清单），0 命中为通过 |

#### 3.5.4 兜底机制（对应 FM-08 / C-08）

输入锁（"动画播放中禁止交换"）的释放条件是"当前批次动画完成"。为避免 FM-08 描述的"渲染回调被节流 → 动画永不完成 → 输入锁永久保持"，设计采用**双触发完成**：

- 主触发：动画进度由渲染循环推进，达到 100% 时正常完成；
- 兜底触发：每个动画批次登记"计划完成时刻 = 启动时刻 + 设计时长 + 200ms 余量"，独立定时器每 500ms 扫描一次，发现超时未完成则直接置为完成态并释放输入锁；
- 完成动作幂等：无论哪个触发先到，都只执行一次（以批次序号去重）。

该机制使"输入锁永久保持"在架构上不可达，是 C-08 的落地实现。

模块边界的三条可检查判据：

1. **数据边界**：M1 只认 `Board`/`Move`/`MatchGroup` 等棋盘层类型，不认识"关卡""星级""金币"；反之 M4 只认识进度层类型，不认识棋盘坐标。
2. **调用边界**：M1 只读调用 M2 的 `scoreEvent` 产出每步得分明细，不判定关卡目标；M3 单向调用 M1/M2；M1/M2 不回调 M3/M4。依赖图固定且无环（AC-A3、K-06）。
3. **所有权边界**：每一份可变数据的唯一所有者——棋盘与冰层布置归 M3 的局内状态；进度（星级/金币/生命/设置）归 M10 的存档；表现态归 M6；队列归 M8。跨模块只能读写对方暴露的接口，不得直接改写对方持有的对象（`readonly` 类型约束）。

### 4.2 关键模块内部结构

#### 4.2.1 M1 棋盘核心引擎（FR-01~FR-07、BR-01、BR-06、BR-10）

内部结构分四段纯函数流水线：

```text
生成段   createBoard(seed, colors) ──► Board
              │  ① 逐格随机填色（5 色均匀）
              │  ② 消除开局就存在的三连（重填该格，最多重试 50 次）
              │  ③ 检测可行交换；无可行交换则整体重排（最多 5 次），仍无解则回到 ①
              ▼
交换段   swapCells(board, a, b) ──► Board'
              │  ④ 仅执行一次位置互换（不做判定，判定在结算段）
              ▼
结算段   settle(board, opts) ──► SettleResult{ 步骤序列, 最终棋盘, 冰层变化, 得分事件 }
              │  ⑤ 找三连（横竖扫描）→ ⑥ 标记消除（含特殊元素连锁触发，按 BR-10 组合表）
              │  ⑦ 冰层减层（元素被消除的格子）→ ⑧ 下落 → ⑨ 顶部补充
              │  ⑩ 若补充后形成新三连则回到 ⑤（连锁计数 +1，上限 8 次）
              ▼
稳定性段 isDeadlock(board) ──► bool（枚举约 112 组合法交换，逐一试算是否形成三连）
         shuffle(board, seed) ──► Board'（重排元素颜色，保留冰层与已有目标进度）
```

关键点说明（均为需求中已明确、设计需给出算法口径的部分）：

| 关键点 | 设计口径 | 依据 |
| ------ | -------- | ---- |
| 开局必有解 | 生成段 ③ 的循环使"开局无可行交换"的概率为 0；单测以 1000 次生成验证（TC-01） | FR-01 |
| 无效交换 | 交换段只做位置互换；结算段若"无任何消除"则返回 `rejected`，由 M3 恢复棋盘且步数、得分不变 | FR-02 |
| 连锁上限 | 结算段的连锁计数达到 8 后停止寻找新三连（此后棋盘保持稳定态） | FR-04、NFR-08 |
| 特殊元素生成 | 一次消除中同一方向的连续同色段长度 = 4 时，在该段中点生成炸弹；长度 ≥ 5 时在该段中点生成彩虹；同一连锁中出现多个满足条件的段时全部生成 | FR-06 |
| 特殊元素组合 | 交换双方均为特殊元素或其一为特殊元素时，按 BR-10 的 6 类情形结算；"被动被消除"（非主动交换）时以该元素所在格为中心按自身规则触发 | FR-06、BR-10 |
| 冰层语义 | 冰层是"格子位置"的属性而非元素的属性（覆盖层模型）：`ice[r][c] ∈ {0,1,2}`，元素被消除时 `ice[r][c] -= 1`（下界 0）；冰层不影响元素能否参与交换；下落与补充不改变冰层 | FR-07、C-01 |
| 锤子与冰层 | 锤子消除目标格元素时，若该格有冰层则同手减 1 层（与普通消除对冰层的处理一致，不额外加成） | FR-22 |
| 死局处理 | 结算段结束（棋盘进入稳定态）后立即调用 `isDeadlock`；死局则调用 `shuffle`（不消耗步数）并提示；连续 5 次洗牌仍死局则重新执行生成段（重建棋盘） | FR-05、FM-02 |
| 重建语义 | 重建只重排元素颜色：保留 `ice` 矩阵、`goalProgress`（已收集数/已破坏冰层数）、`score`、`movesUsed`、`itemUsed` 记录（对应 FR-05 的"重建语义"段） | FR-05、C-10 |

#### 4.2.2 M2 计分系统（FR-04、FR-16、NFR-08）

M2 以"得分事件"为输入：一次结算产生一个 `ScoreEvent` 序列（每个事件描述一批被消除的元素与该批的特殊元素奖励），M2 输出 `ScoreBreakdown`。

```text
基础分      = 被消除元素数 × 10
连锁系数    = 1 + 0.5 × (连锁序号 − 1)，连锁序号 1..8，系数范围 1..4.5
特殊奖励    = 炸弹 100/个 + 彩虹 300/个（按"触发"计，而非按"生成"计）
得分        = Σ 每批 ( 该批基础分 × 该批连锁系数 ) + Σ 特殊奖励
```

M2 同时提供两个**理论常量**供 M9 与服务端复用：`S_MAX = 64 × 10 × 4.5 + 600 = 3480`（单步上限）与 `TOTAL_MAX = 615 × 3480 = 2,140,200`（总积分硬上限，615 为 ΣM(n)，见 §7.3、§13.2 K-03）。M2 不拦截超限分数——拦截发生在提交链路上（§9.3）。

#### 4.2.3 M3 关卡流程引擎（FR-07、FR-08、FR-09、FR-22、FR-23）

M3 维护一次对局的完整运行时状态（`RunState`，见 §7.4），对外暴露 `applyMove` 与 `useItem` 两个动作：

| 动作 | 步骤 | 判定结果 |
| ---- | ---- | -------- |
| `applyMove(a, b)` | ① 校验是否相邻（否则拒绝，不消耗步数）→ ② 调用 M1 `settle` → ③ 若 `rejected` 则恢复棋盘、返回 `rejected` → ④ 消耗 1 步、累加得分 → ⑤ 更新目标进度（收集计数、冰层破坏数）→ ⑥ 判失败（步数耗尽且任一目标未达成）→ ⑦ 判达成（全部目标达成）→ ⑧ 死局检测与洗牌 | `applied / rejected / clear / fail` |
| `useItem(kind, target?)` | ① 校验该关该道具未用过且库存 ≥ 1（否则拒绝）→ ② 依次执行效果（重排 / 锤子 / +5 步）→ ③ 道具效果引起的消除同样走 M1/M2 结算、同样更新目标进度 → ④ 记录"本关已用"、扣库存 → ⑤ 与 `applyMove` 相同的达成/失败判定 | `applied / rejected / clear / fail` |

判定口径（对齐需求中的关键分支）：

| 分支 | 口径 | 依据 |
| ---- | ---- | ---- |
| 达成时机 | 第 ⑦ 步在**本次动作结算完成后立即执行**：全部目标达成的那一手即刻结算，不消耗剩余步数、不再接受输入 | FR-09、C-07 |
| 收集目标计数 | 统计"被消除元素中指定颜色的个数"，锤子与特殊元素造成的消除同样计入 | FR-07、FR-22 |
| 冰层目标计数 | 仅当某格冰层由 1 变 0 时计入 1；双层冰第一次消除（2→1）不计入 | FR-07 |
| 失败口径 | 仅当 `movesLeft == 0` 且存在未达成目标时判失败；失败不扣金币与道具 | FR-08 |
| 道具不消耗步数 | `useItem` 不改变 `movesLeft`（+5 步道具除外，它加 5） | FR-22 |
| 每关每种道具限用 1 次 | `itemUsed` 记录跨重试保留在**本局对局**内；返回主菜单再进入视为新对局；对局内失败重试是否继承按 §13.3 的条款解释处理 | FR-22、§13.3 |
| 结算期间输入 | M3 进入 `clear/fail` 终态后，`applyMove`/`useItem` 一律返回 `locked`，防止重复结算 | FR-09、FM 语义 |

#### 4.2.4 M4 经济与进度系统（FR-09~FR-15、FR-23、BR-07~BR-09）

| 能力 | 输入 | 输出与口径 | 依据 |
| ---- | ---- | ---------- | ---- |
| 星级判定 | 剩余步数、`starKeep` | `stars = 3 if 剩 ≥ keep3; 2 if 剩 ≥ keep2; else 1`；重复通关取历史最高星 | FR-09、BR-07 |
| 奖励已发放星级 | 关卡号、本局星级、`rewardPaidStars` | 返回"应发金币 + 更新后的 `rewardPaidStars`"：本局星级高于记录时按两档差额补发并更新；不高于时按本局星级奖励的 50%（向下取整） | FR-23、BR-08 |
| 解锁 | 关卡号、本局星级 | 星级 ≥ 1 且该关首次通过时 `unlockedLevel = max(unlockedLevel, n+1)` | FR-11 |
| 总积分 | 各关最高分 | `totalScore = Σ bestScores[n]`，重玩低分不下降 | FR-17 |
| 道具购买 | 道具类型、余额 | 余额不足返回 `insufficient`（不扣款、不改库存） | FR-23、FM-14 |
| 生命消耗与恢复 | 失败事件、当前时间、锚点 | 失败 `lives−1`；恢复按"锚点 + 已恢复次数 × 15min"推进；时间回拨时"已过时间"钳为 0 | FR-14、FM-07 |
| 生命补满 | 余额、当前生命 | 余额 ≥ 200 才允许：扣 200、生命置 5；否则返回 `insufficient` 与差额 | FR-14、FM-14 |

M4 的所有函数把"时间"作为显式参数（`now`、锚点），不读系统时钟，这是 FM-07 的时间篡改防护能在单测中被精确构造的前提。

### 4.3 状态流与所有权

数据流是单向的：

```text
输入（M8 队列）
   └─► M5 取出一个 InputIntent
         └─► 调用领域层（M3.applyMove / useItem，或 M4/M11 的纯函数）
               └─► 返回 新 RunState + 事件序列
                     ├─► M10 更新内存状态（必要时落盘，见 §5.3）
                     ├─► M6 收到事件 → 播放动画 → 动画完成事件回给 M5 → M5 解锁输入
                     ├─► M7 收到事件 → 播放音效
                     └─► M5 重新生成 ViewState → M6 下一帧绘制
```

三条规则：

1. **单一事实源**：进度类状态只存于 M10；对局类状态只存于 M5 持有的当前 `RunState`；两者都不可被其他模块改写。
2. **快照只读**：M6 每个帧只读 `ViewState`（M5 生成），不得回写。
3. **事件即事实**：所有"发生了什么"以事件序列表达（如 `tiles:cleared`、`ice:broken`、`goals:changed`、`score:changed`），M6/M7 只响应事件，不自行推断。

### 4.4 事件通道与输入序列化

| 通道 | 发布者 | 载荷要点 | 订阅者与用途 |
| ---- | ------ | -------- | ------------ |
| `input:intent` | M8 | 语义化输入（点击/滑动/按键/按钮） | M5 唯一消费者 |
| `input:lock` / `input:unlock` | M5 | 锁原因（动画批次号） | M8（决定是否排队） |
| `board:settled` | M3 | 结算步骤序列（消除批次、下落路径、补充列） | M6 播放动画、M7 播消除音 |
| `score:changed` | M3 | 得分明细（基础分/连锁系数/特殊奖励/累计） | M6 刷新 HUD、UI-4 弹窗明细 |
| `goals:changed` | M3 | 各目标当前值与差值 | M6 刷新目标面板 |
| `ice:broken` | M3 | 被破坏的格子坐标 | M6 播放冰层碎裂效果、M7 音效 |
| `deadlock:shuffled` | M3 | 洗牌次数、是否触发重建 | M5 显示"无可消除组合，已自动重排"提示 |
| `run:clear` / `run:fail` | M3 | 结算载荷（得分、剩余步数、星级、未达成目标与差值） | M5 编排结算流程（FL-02） |
| `save:changed` | M10 | 变更字段集合、写入结果 | M5 刷新依赖进度的界面、提示保存失败 |
| `save:external` | M10 | 其他标签页写入后的合并结果 | M5 提示"进度已从其他标签页更新" |
| `leaderboard:state` | M9 | 提交状态机当前态（idle/submitting/ok/degraded） | M5 刷新排行榜页与按钮态 |
| `visibility:changed` | 平台事件（M7 转发） | 前台/后台 | M7 自身（音乐暂停/恢复） |

**输入序列化规则（FR-25 的落地）：** 动画期间到达的 `InputIntent` 进入 M8 队列（容量 2，先进先出，超出则丢弃最旧）；M5 在 `input:unlock` 后逐个取出执行；队列中的意图在被取出时**重新校验有效性**（例如目标格已被消除则丢弃）。这样"动画期间连续点击两次交换，两次请求均被依次执行"（TC-27）有确定实现。

**幂等与去重：** 每个动画批次带自增序号，M8 的去重与 M6 的兜底完成都以批次序号为键，保证 §3.5.4 的双触发不产生重复完成动作。

### 5.1 FL-01 消除结算与连锁（FR-02、FR-03、FR-04、FR-05、FR-06、FR-16、FR-25）

```text
M8/M5        M3                  M1                    M2         M6/M7        M10
  │ 交换意向   │                   │                     │            │           │
  ├───────────►│ applyMove(a,b)    │                     │            │           │
  │            ├─① 相邻校验 ────────┤                     │            │           │
  │            │   （不相邻→拒绝）   │                     │            │           │
  │            ├─② swapCells ─────►│                     │            │           │
  │            ├─③ settle ────────►│ 找三连→标记消除      │            │           │
  │            │                   │ →冰层减层→下落→补充   │            │           │
  │            │                   │ →连锁（≤8 次）        │            │           │
  │            │◄── SettleResult ──┤                     │            │           │
  │            ├─④ rejected？─────────────────────────────►│ 恢复棋盘    │
  │            ├─⑤ movesLeft −1    │                     │            │           │
  │            ├─⑥ score 累加 ─────────────────────────► │ 明细         │
  │            ├─⑦ goals 更新       │                     │            │           │
  │            ├─⑧ board:settled / score:changed / goals:changed / ice:broken ───►│
  │            │                   │                     │            ├─ 动画/音效 │
  │            ├─⑨ 达成？fail？ ──► 见 FL-02             │            │           │
  │            ├─⑩ isDeadlock？ 是→ shuffle → deadlock:shuffled ────► │           │
  │            ├─⑪ 落盘（若本步改变了持久化字段）──────────────────────────────────►│

```

**正常路径：** 步骤 ①~⑪ 全程无异常时，一次交换在 ≤ 2.4s 内完成可视化（消除 0.4s + 下落 0.3s + 补充 0.3s、多段连锁按 3 段上限计约 1.5s，另留余量），期间输入被排队。

**分支路径：**

| 分支 | 条件 | 行为 |
| :--: | ---- | ---- |
| B1 | 交换不相邻（滑动位移 < 0.3 格或点击的两格不相邻） | 步骤 ① 直接拒绝，不进入结算，不消耗步数、不产生动画（FR-02、FR-28） |
| B2 | 交换合法但不形成三连 | 步骤 ④：播回弹动画（≤ 0.2s）并恢复棋盘，返回 `rejected`，步数与得分不变（FR-02） |
| B3 | 本次消除形成 4 连 / ≥5 连 | 生成炸弹 / 彩虹后再进入下落补充；同批多段满足条件时全部生成（FR-06） |
| B4 | 交换涉及特殊元素或连锁触发特殊元素 | 按 BR-10 组合表结算：炸弹×炸弹（5×5）、炸弹×彩虹（最多色转炸弹再依次触发）、彩虹×彩虹（清空）、特殊×普通（各自规则）、被动消除（以自身格为中心触发）（FR-06、BR-10） |
| B5 | 结算后棋盘死局 | 步骤 ⑩ 自动洗牌（不消耗步数）并提示"无可消除组合，已自动重排"；连续 5 次洗牌仍死局则重建棋盘（FR-05、FM-02） |
| B6 | 洗牌/重建发生时冰层与目标进度已存在 | 按"重建语义"保留冰层布局、已收集数、已破坏冰层数、得分、已用步数与道具记录（FR-05、C-10） |
| B7 | 一次结算中连锁达到第 8 次 | 停止继续寻找新三连，棋盘直接进入稳定态（FR-04、NFR-08 的系数上限 4.5） |
| B8 | 动画期间玩家继续输入 | 输入进入 M8 队列（容量 2），解锁后依序执行，执行前重新校验（FR-25、TC-27） |

**异常路径：**

| 异常 | 触发 | 处理与恢复 | 关联 |
| ---- | ---- | ---------- | ---- |
| E1 | 渲染回调被节流（切后台/无渲染环境） | M6 的兜底检查（每 500ms）在超过"计划完成时刻"后强制完成动画并释放输入锁；完成动作幂等 | FM-08、C-08、§3.5.4 |
| E2 | 结算期间标签页被关闭 | 结算结果若已落盘则保留；未落盘则回到上一个已落盘状态（本步不计），重新打开后可继续游玩 | NFR-14、§5.3 |
| E3 | 步骤 ⑪ 落盘失败（隐私模式/配额满） | 捕获异常并进入"不可保存模式"：本局继续，顶部提示"当前浏览器环境无法保存进度，关闭页面后可能丢失"，后续不再重试写入 | FM-01、NFR-07 |

**分支路径：**

| 分支 | 条件 | 行为 |
| :--: | ---- | ---- |
| B1 | 剩余步数满足 3★ 阈值（≥ keep3） | 星级 = 3★，金币按 3★ 档结算 |
| B2 | 剩余步数满足 2★ 阈值（≥ keep2）但不满足 3★ | 星级 = 2★ |

| B8 | 步数耗尽且任一目标未达成 | 判失败：生命 −1（FL-06）、弹失败弹窗并列出未完成目标与差值（如"冰层目标 8/10，还差 2 层"） |
| B9 | 达成瞬间仍有剩余步数 | 立即结算，**不**继续消耗剩余步数（FR-09、C-07） |
| B10 | 结算期间玩家继续点击棋盘 | M3 已处于终态，输入被丢弃（`locked`）；弹窗上的按钮仍可用 |
| B11 | 达成与失败在同一手同时可能成立（步数恰好用尽但目标已达成） | 先判"达成"：全部目标已达成即结算胜利，失败判定不生效（FR-09 的"达成即结算"优先于 FR-08） |

**异常路径：**

| 异常 | 触发 | 处理与恢复 | 关联 |
| ---- | ---- | ---------- | ---- |
| E1 | 结算落盘失败 | 与 FL-01/E3 相同：进入"不可保存模式"并提示，本局结果仍可正常展示 | FM-01 |
| E2 | 结算弹窗期间标签页被关闭 | 进度已先落盘（步骤 ① 先于弹窗）；重新打开后该关已计入通关，奖励不重复发放（`rewardPaidStars` 已更新） | NFR-14、FR-23 |
| E3 | 星级阈值数据非法（`keep2 ≥ keep3` 或越界） | 关卡配置校验（§7.3）在启动时已拒绝该条并回落默认配置；运行时不再出现非法阈值 | FM-12 |
| E4 | 同一关在一局中重复触发结算事件 | 事件带对局序号，M5 只处理序号最新且未处理过的 `run:clear/run:fail`，重复事件被忽略 | FR-09 的"防止重复结算"语义 |

### 5.3 FL-03 进度持久化与写盘时机（FR-12、FR-15、NFR-14）

**正常路径：** 状态变更 → M10 组装存档对象（`DS-1` 结构）→ 写入 localStorage 键 `gemz_save_v1` → 广播 `save:changed`。

写盘时机（对齐 FR-12 的"每次状态变更后同步写入"，并明确"哪些变更立即写、哪些合并写"）：

| 触发变更 | 写盘策略 | 理由 |
| -------- | -------- | ---- |
| 结算完成（星级/金币/解锁/最高分/总积分/`rewardPaidStars`） | **立即同步写** | 最重要的进度，直接对应 NFR-14 |
| 关卡失败（生命 −1） | 立即同步写 | 生命与锚点必须原子落盘，避免刷新后生命回涨 |
| 生命恢复结算 | 立即同步写 | 锚点与已恢复次数同步推进 |
| 购买道具 / 补满生命 | 立即同步写 | 金币与库存须一致 |
| 道具在局内被使用（库存 −1） | 立即同步写 | 避免"刷新规避消耗" |
| 局内步数/得分/目标进度 | **不写盘** | 对局是可丢弃状态（NFR-14 只要求"已完成关卡进度"不丢）；避免每步写盘 |
| 设置项（静音、色盲） | 立即同步写（轻量） | 与 FR-26/FR-30 的"持久保存"对齐 |
| 昵称变更 | 立即同步写 | 排行榜身份 |

**分支与异常路径：**

| 情形 | 条件 | 行为 |
| ---- | ---- | ---- |
| B1 | 键不存在（首次游玩） | 以默认存档启动：`unlockedLevel=1`、`stars={}`、`bestScores={}`、`totalScore=0`、`coins=0`、道具各 1、`lives=5`、`livesUpdatedAt=now`、`livesRestored=0`、`muted=false`、`colorblind=false`、`nickname=""`、`rewardPaidStars={}` |
| B2 | 存档 `version` 低于当前版本 | 依次执行迁移函数链（v1→v2→…），迁移后再补齐缺省字段 |
| B3 | 缺字段 / 类型不符 | 逐字段按默认值补齐（不丢已验证字段），并记录一条日志；（不能解析的 JSON 见 E1） |
| B4 | 存档为"不可保存模式"下运行 | 内存态继续工作，不再尝试写盘；每次会话开始时重新探测一次可写性 |
| E1 | JSON 解析失败 | 把原值备份到临时键 `gemz_save_v1.corrupt.<时间戳>`，以默认存档启动并提示"存档已损坏，已备份并重置" |
| E2 | 写入抛异常（隐私模式 / 配额满 / 被禁用） | 捕获并置"不可保存"标志；顶部提示条常驻；本局与进度逻辑不受影响 |
| E3 | 多标签页并发写（详见 FL-04） | 写前比对 `updatedAt`，按合并规则处理 |

### 5.4 FL-04 多标签页写入合并（FM-13、FR-12、FR-15）

```text
标签页 A                         localStorage                     标签页 B
 │ 写盘前 read 当前存档 ───────────►│◄─────────── 写盘前 read ────────│
 │ 比对 updatedAt：                │                                 │
 │  · 本地内存较新 → 直接写         │                                 │
 │  · 本地内存较旧 → 先重载并合并： │                                 │
 │     unlockedLevel = max(A,B)     │                                 │
 │     stars         = 逐关 max     │                                 │
 │     bestScores    = 逐关 max     │                                 │
 │     totalScore    = 按合并后 bestScores 重算（= Σ max）             │
 │     coins/items/lives = 取时间戳较新一方的值（非累加）              │
 │     设置项/昵称   = 取时间戳较新一方的值                            │
 │ 合并后再写 ────────────────────►│                                 │
 │                                 ├─► storage 事件 ────────────────►│
 │◄─ 收到 B 的变更 → 同样执行合并 → 提示"进度已从其他标签页更新" ──────┤
```

**设计口径（针对 FM-13 的"取较大值"要求给出逐字段规则）：**

| 字段类型 | 合并规则 | 说明 |
| -------- | -------- | ---- |
| 单调递增类（`unlockedLevel`、`stars[n]`、`bestScores[n]`、`rewardPaidStars[n]`） | 逐项取较大值 | 这类字段"后退"只会是覆盖事故，取大值即无损 |
| 派生类（`totalScore`） | 按合并后的 `bestScores` 重新求和 | 保证 `totalScore = Σ bestScores` 的恒等式不被破坏 |
| 可消耗资源（`coins`、`items`、`lives`） | 取 `updatedAt` 较新一方的值 | 不能取大值（会凭空造币），也不能求和（会重复计数）；以"最近操作者为准" |
| 设置类（`muted`、`colorblind`、`nickname`） | 取 `updatedAt` 较新一方的值 | 用户显式设置项，以最新意图为准 |
| 锚点类（`livesUpdatedAt`、`livesRestored`） | 与所属分支的 `lives` 同源（同一方） | 锚点与恢复次数必须成对，不能跨方拼接 |

**异常路径：**

| 异常 | 触发 | 处理 | 关联 |
| ---- | ---- | ---- | ---- |
| E1 | 两个标签页几乎同时写（毫秒级交错） | `updatedAt` 相同或差距 < 1ms 时，以"字段并集 + 取大值"的保守规则合并（可消耗资源取本地现有值），保证不出现比存储更旧的状态 | FM-13 |
| E2 | 合并过程中再次收到 `storage` 事件 | 合并操作串行化（单飞：进行中时把新事件挂起，合并完成后再处理一次） | FM-13 |
| E3 | 本标签页处于"不可保存模式" | 只接收合并结果、不写盘；提示用户该页更改不会被保存 | FM-01、FM-13 |
| E4 | 当前正在对局中收到外部进度更新 | 对局不中断（按 FM-13 要求）；仅在结算时把对局结果与合并后的进度再合并 | FM-13 |

 ├──────────────────►│ ① 组装 {nickname,totalScore}              │

### 5.6 FL-06 生命恢复与时间篡改（FR-14、FM-07、FM-14）

```text
M5                       M4                                    M10
 │ 每次关注操作前/每 60s   │                                      │
 ├───────────────────────►│ restoreLives(now, anchor, restored)   │
 │                        │  elapsedTotal = now − anchor          │
 │                        │  elapsed = max(0, elapsedTotal)  // 回拨钳为 0
 │                        │  gained = ⌊elapsed / 15min⌋ − restored │
 │                        │  若 gained > 0：                      │
 │                        │    lives = min(5, lives + gained)      │
 │                        │    restored += gained                 │
 │                        │    anchor' = anchor + gained × 15min  // 不用 now
 │◄── {lives, anchor', restored} ──┤                               │
 ├─ 若有变化 → 立即落盘 ──────────────────────────────────────────►│
```

**正常路径：** 距锚点每满 15 分钟恢复 1 点，最多 5 点；锚点与已恢复次数成对推进。

**分支与异常路径：**

| 情形 | 条件 | 行为 |
| ---- | ---- | ---- |
| B1 | 生命已满 5 | 恢复逻辑不推进锚点（保持当前锚点），显示"生命已满" |
| B2 | 一次检查跨越多个恢复周期（如离线 47 分钟） | 一次性恢复 ⌊47/15⌋ = 3 点（受上限 5 截断），锚点推进 45 分钟 |
| E1 | 系统时间回拨（now < anchor） | "已过时间"钳为 0：不恢复、不扣减、不重置；锚点保持 | 
| E2 | 系统时间大幅前拨 | 按 ⌊elapsed/15min⌋ 恢复但受上限 5 截断；锚点仅按"锚点 + 恢复次数 × 15min"推进（不直接取 now），因此前拨不能刷新出"无限恢复" |
| E3 | 生命为 0 时尝试补满但金币 < 200 | 按钮置灰，提示"金币不足，还差 N 点"，不扣金币、不改生命（与 FM-14 一致） |
| E4 | 生命为 0 且金币 ≥ 200 | 扣 200 金币、生命置 5、锚点重置为 now、`livesRestored = 0`，立即落盘 |

## 6. 接口设计

**承接需求：** FR-12/FR-13（存档读写与导入导出）、FR-18~FR-21（排行榜两接口）、FR-22/FR-23（道具与金币）、FR-14（生命）、FR-25（输入队列）、NFR-08（校验）、NFR-09（仅两个后端接口）。

本章接口分两部分：**内部模块接口**（35 个，编号 I-01~I-35，按模块列出，含用途、输入、输出、错误约定与调用限制）与**外部接口**（HTTP-1/HTTP-2 两个后端接口，含请求响应格式、错误码与调用限制，以及 FR-13 的存档导入/导出文件接口）。全部签名以 TypeScript 风格给出；`DS-1~DS-4` 为 §7 定义的数据结构。所有接口的错误约定统一为：**非法输入返回显式失败结果（不抛异常、不产生副作用），环境性异常只在系统边界捕获并降级**——这条约定是 §9.7 故障处理设计的实现基础。

### 6.1 公共类型定义（接口的输入输出基础）

```ts
type Pos   = readonly [row: number, col: number];          // 0 ≤ row,col ≤ 7
type TileKind = 0 | 1 | 2 | 3 | 4 | 'bomb' | 'rainbow' | null;   // null = 空格（过渡态）
interface Tile { readonly kind: TileKind; readonly id: number }   // id 用于动画追踪元素身份
interface Ice  { readonly layers: 0 | 1 | 2 }              // 覆盖层模型：冰层属于格子（FR-07/C-01）
interface Board {                                           // 不可变值对象，任何操作都返回新 Board
  readonly rows: 8; readonly cols: 8;
  readonly tiles: readonly (readonly Tile[])[];            // 8×8
  readonly ice: readonly (readonly Ice[])[];               // 8×8，与 tiles 同形
}
type Move = { readonly from: Pos; readonly to: Pos };       // 交换/锤子落点等动作的统一定义

type GoalKind = 'score' | 'collect' | 'ice';
interface GoalStatus { readonly kind: GoalKind; readonly current: number;
                       readonly target: number; readonly done: boolean }
interface GoalProgress { readonly score: number; readonly collect: number; readonly iceBroken: number }

interface ScoreEvent {                                      // 一次结算中的一批消除（M1→M2）
  readonly chain: number;                                   // 连锁序号 1..8
  readonly clearedCount: number;                            // 该批被消除元素数
  readonly bombsTriggered: number; readonly rainbowsTriggered: number;
}
interface ScoreBreakdown {                                  // 得分明细（FR-16、FR-32 弹窗用）
  readonly base: number; readonly chainFactor: number; readonly specialBonus: number;
  readonly stepTotal: number; readonly runTotal: number;
}
interface CascadeStep {                                     // 回放一段连锁所需的全部信息（M1→M6）
  readonly chain: number;
  readonly cleared: readonly Pos[];                          // 本批被消除格
  readonly iceBroken: readonly Pos[];                        // 本批冰层由 1→0 的格
  readonly iceReduced: readonly Pos[];                       // 本批冰层由 2→1 的格
  readonly spawned: readonly { at: Pos; kind: 'bomb' | 'rainbow' }[];
  readonly falls: readonly { from: Pos; to: Pos }[];         // 下落路径
  readonly refills: readonly { at: Pos; kind: TileKind; id: number }[];  // 顶部补充
  readonly score: ScoreBreakdown;
}
interface SettleResult {
  readonly variant: 'applied' | 'rejected';                  // rejected = 未形成消除（FR-02）
  readonly board: Board;                                     // 结算后的棋盘
  readonly steps: readonly CascadeStep[];                    // 连锁序列，可直接驱动动画
  readonly totalScoreDelta: number;
}
interface TileEvent { readonly kind: 'pointer' | 'tap' | 'drag' | 'hotkey';
                      readonly at?: Pos; readonly to?: Pos; readonly key?: string }
interface ViewState {                                        // 只读视图快照（M5→M6，§4.3 规则 2）
  readonly scene: 'menu' | 'levelSelect' | 'playing' | 'rank' | 'settings';
  readonly board?: Board;
  readonly goals?: readonly GoalStatus[];
  readonly score?: number; readonly movesLeft?: number;
  readonly starsPreview?: 1 | 2 | 3;                         // 局内星级预告（FR-10）
  readonly starKeep?: { keep2: number; keep3: number };
  readonly lives: number; readonly coins: number;
  readonly items: { shuffle: number; hammer: number; plus5: number };
  readonly muted: boolean; readonly colorblind: boolean;
  readonly dialog?: DialogSpec | null;                       // 弹窗描述（UI-3/UI-4）
}
interface DialogSpec { readonly id: string; readonly type: 'win' | 'fail' | 'info' | 'confirm';
  readonly lines: readonly { label: string; value: string }[]; readonly actions: readonly string[] }
type Clock = () => number;                                   // 毫秒时间戳；FM-07 的注入点
type Rng = () => number;                                     // [0,1)；棋盘/冰层/榜单的可注入随机源
```

### 6.2 接口清单

#### 6.2.1 M1 棋盘核心引擎（5 个）

| 编号 | 签名 | 用途 | 错误约定 | 调用限制 |
| :--: | ---- | ---- | -------- | -------- |
| I-01 | `createBoard(rng: Rng, colors = 5): Board` | 生成开局必有解的棋盘（FR-01） | 内部最多重试 50 次填色 + 5 次整体重排；仍失败（理论不可达）返回最后一次结果并广播 `board:generate_fallback` 日志事件 | 纯函数；单次 ≤ 5ms（64 格）；不得在动画帧内重复调用 |
| I-02 | `settle(board: Board, move: Move, opts): SettleResult` | 执行一次交换并完成全部连锁结算（FR-02~FR-06），返回可直接驱动动画的步骤序列 | `move` 越界/不相邻 → 抛 `RangeError`（属编码错误，调用方 M3 在调用前已完成相邻校验）；无消除 → 返回 `variant='rejected'` 且 `board` 为交换前状态 | 纯函数；只读 `board`；`opts` 含 `rng`（洗牌用）与 `chainLimit=8`；单次 ≤ 50ms |

### 6.3 外部接口

#### 6.3.1 HTTP-1 排行榜提交 `POST /api/score`

| 项目 | 内容 |
| ---- | ---- |
| 用途 | 提交玩家总积分，返回当前名次（FR-18、FR-19、FR-21、NFR-08） |
| 请求头 | `Content-Type: application/json` |
| 请求体 | `{ "nickname": "星消乐玩家", "totalScore": 18600 }` |
| 成功响应 | `200` + `{ "code": 0, "rank": 5 }` |
| 错误响应 | `200` + `{ "code": 1001 \| 1002 \| 5000, "msg": "string" }`（业务错误统一用 200 + code，便于浏览器端统一处理；HTTP 5xx 视为 5000 语义） |
| 超时 | 客户端 3 秒（FR-20）；超时即中置请求并按 FM-03 降级 |
| 调用限制 | 昵称 3–12 字符、字符集 `[中英文][0-9][_]`；`totalScore` 为整数且 0 ≤ 值 ≤ 2,150,000（拒绝阈值，见 §9.3）；服务端按同名昵称保留最高分并更新时间戳与自增序号；同一昵称 10 秒内最多接受 1 次有效写入（其余返回最近一次结果，保证 FR-21 的窗口稳定） |

**服务端校验序（与 NFR-08 的"白名单过滤 + 长度校验 + 上限校验"逐条对应）：**

```text
① 长度与字符集白名单（正则）；不满足 → 1001（含 HTML 片段、空白、控制字符的情形）
② totalScore 类型与整数性；不满足 → 1002
③ 0 ≤ totalScore ≤ 2,150,000；不满足 → 1002（5000 用于内部错误）
④ 完成写入 → 计算名次并返回 {code:0, rank}
```

#### 6.3.2 HTTP-2 排行榜查询 `GET /api/rank?limit=100`

| 项目 | 内容 |
| ---- | ---- |
| 用途 | 拉取榜单前 N 名（FR-18） |
| 请求参数 | `limit` 可选，默认 100，范围 1..100（越界钳到界内） |
| 成功响应 | `{ "code": 0, "list": [ { "rank": 1, "nickname": "星消乐玩家", "totalScore": 18600, "avatar": null } ] }` |
| 错误响应 | `{ "code": 5000, "msg": "..." }` 或 HTTP 5xx |
| 超时 | 客户端 3 秒，超时触发 FR-20 降级 |
| 调用限制 | 榜长度上限 100；`avatar` 本版本恒为 `null`（客户端以星形宝石占位图渲染，不请求外部图片）；进入排行榜页时拉取一次，同页面 10 秒内不重复拉取 |
| 排序规则 | `totalScore DESC, submitSeq ASC`（`submitSeq` 为服务端自增序号，作为同分次序键——FR-21/FM-11 的稳定名次由它保证，并以 10 秒结果缓存窗口对外表现稳定） |

#### 6.3.3 存档导入/导出的文件接口（FR-13）

| 项目 | 内容 |
| ---- | ---- |
| 导出 | 生成文件名 `gemz-save-v1-YYYYMMDD.json`，内容为 `DS-1` 的完整 JSON；由浏览器下载（`Blob` + `a[download]`），不发送到任何服务器 |

| 校验失败 | 在导入对话框内逐条列出失败原因（如"字段 `coins` 类型应为非负整数，实际为字符串"）；**不修改当前存档** |
| 校验通过 | 弹确认框（展示"关卡进度 / 总积分 / 金币"三项摘要）→ 确认后整体替换并落盘，落盘失败按 FM-01 处理 |
| 限制 | 文件大小上限 256KB（远大于实测 < 2KB，用于防呆）；不解析除 JSON 外的任何格式 |

#### 6.3.4 接口与数据、流程的一致性核对

| 核对项 | 结论 |

## 7. 数据设计

**承接需求：** DS-1 承接 FR-12/FR-13/FR-14/FR-15/FR-23/FR-26/FR-30 与 FM-01/FM-07/FM-10/FM-13；DS-2 承接 FR-07/FR-09/FR-10 与 NFR-10/FM-12；DS-3 承接 FR-18/FR-21 与 NFR-08/FM-11；DS-4 为运行态载荷。四份数据与 §6 的接口、§8 的界面字段、§2.3 的数值基线一一对应，对应关系在本章末尾（§7.6）逐项核对。

### 7.1 数据设计总览

| 编号 | 数据 | 介质 | 生命周期 | 所有者 | 版本化 |
| :--: | ---- | ---- | -------- | ------ | ------ |
| DS-1 | 玩家存档 `SaveV1` | localStorage 键 `gemz_save_v1` | 跨会话持久 | M10 | 有（`version` 字段 + 迁移链） |
| DS-2 | 关卡配置 `levels.json` | 构建期静态资源 | 随版本发布 | M11 | 有（`version` 字段） |
| DS-3 | 排行榜数据 | 服务端 SQLite | 永久（服务端） | 排行榜服务 | 无（表结构由服务端迁移管理） |
| DS-4 | 对局运行时快照 `RunState` | 内存 | 单局 | M5（经 I-09/I-10/I-11 产生） | 无（可随时丢弃） |

数据分类原则：**只持久化"不可重算"的数据**。对局内可重算的中间状态（棋盘、步数、目标进度）一律不落盘（§5.3 的写盘时机表），因此 DS-1 结构小（实测 < 2KB），localStorage 的 5MB 容量余量充裕。

#### 7.3.3 冰层布置算法（BR-06、C-05 的落地实现）

BR-06 要求"按各行被消除频率加权布置，而非均匀随机"，但未给出可实现的算法。设计给出如下确定性口径（对应 §13.2 K-02）：

```text
输入：I(n)（冰层格数）、doubleRatio、rng（可注入种子）
输出：ice[8][8]（每格 0/1/2 层）

① 行权重：w[r] = 64 × f[r] / Σf，其中 f 取 V-14 实测的 200 局消除频率分布
     f = [0.18, 0.18, 0.18, 0.15, 0.12, 0.09, 0.06, 0.044]
     归一化后（保留 1 位小数，末行取余数）：
     w = [12.0, 12.0, 12.0, 10.0, 8.0, 6.0, 4.0, 0.0]，合计 64.0
② 逐格权重：cellW[r][c] = w[r]（行内格等权，8 格均分）
③ 无放回加权抽样 I(n) 个格：每格被抽中概率 ∝ cellW[r][c]
     —— 第 7 行权重为 0，即"几乎不会被消除的底行不再布置冰层"（V-14 结论的直接体现）
④ 层数分配：在抽中的格中，取 round(I(n) × doubleRatio) 格置 2 层，其余置 1 层
⑤ 结果由种子 rng 决定，同一种子可复现；同一关重试（重试进入新对局）时重新布置
```

**设计理由：** 权重与"被消除频率"成正比是 BR-06 的唯一要求；把底行权重压到 0 是把 V-14 的统计结论（底行频率 4.4%，均匀布置会导致约 1/4 冰格不可达）直接编码为约束，比"给底行一个极小权重"更可验证——TC-39 的通过率若在段 3 达标，即可反证该布置合理。该权重向量是常量表，不随关卡变化，实现与测试都只需一张 8 行表。

### 7.4 DS-3 排行榜服务数据

#### 7.4.1 表结构（SQLite）

```sql
-- 榜单主表：每个昵称一条记录（同名保留最高分）
CREATE TABLE score (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,   -- 自增序号：同分次序键（FR-21 / FM-11）
  nickname     TEXT    NOT NULL,                    -- 3–12 字符，白名单校验后入库
  total_score  INTEGER NOT NULL CHECK (total_score >= 0),
  created_at   TEXT    NOT NULL,                    -- 首次提交时间（ISO 8601，UTC）
  updated_at   TEXT    NOT NULL,                    -- 最近一次有效提交时间

-- 写入节流表：同一昵称 10 秒内只接受 1 次有效写入（FR-21 的窗口稳定）
CREATE TABLE submit_throttle (
  nickname     TEXT    PRIMARY KEY,
  last_seq     INTEGER NOT NULL,                    -- 最近一次有效写入的 score.id
  last_time    INTEGER NOT NULL                     -- 最近一次有效写入的毫秒时间戳
);
```

| 字段 / 约束 | 说明 | 对应需求 |
| ----------- | ---- | -------- |
| `nickname` UNIQUE | 昵称即身份；同名重复提交是"更新"而非"新增" | FR-18、FR-19 |
| `total_score` CHECK ≥ 0 | 数据库层兜底；应用层另有 ≤ 2,150,000 的拒绝阈值 | NFR-08 |
| `id` 自增序号 | 同分时的次序键（先提交者靠前），且不因时间戳调整而抖动 | FR-21、FM-11 |
| 名次计算 | 查询时以窗口函数 `RANK() OVER (ORDER BY total_score DESC, id ASC)` 计算，不物化存储（榜单规模 ≤ 10⁴ 行，实时计算开销可忽略） | FR-18、FR-21 |
| 节流窗口 | 同一昵称 10 秒内第 2 次及以后的提交直接返回 `last_seq` 对应的名次（不写入），保证窗口内结果稳定 | FR-21 |
| 无账号表 | 不建用户表、不存密码、不存设备指纹（OO-03、OO-07） | NFR-09 |

#### 7.4.2 生效规则

| 项目 | 规则 |
| ---- | ---- |
| 写入流程 | ① 白名单与长度校验（失败 → 1001）→ ② 类型与上限校验（失败 → 1002）→ ③ 节流查询（窗口内 → 直接返回当前名次）→ ④ UPSERT：新昵称插入；已有昵称仅在 `total_score` 更高时更新（同时更新 `updated_at`）→ ⑤ 计算名次并返回 |

| 无付费 | 界面无付费入口、无充值弹窗、无外部支付跳转；代码中不引入任何支付 SDK | 全界面走查（TC-26） |

### 9.7 异常与故障处理设计（FM-01~FM-14）

**处理总则：** ① 环境性异常只在系统边界（存储、网络、音频、渲染回调）捕获，捕获后一律转为"降级状态 + 用户提示"，不向玩法逻辑传播；② 玩法逻辑内部不产生异常路径（非法输入在接口层就返回显式失败结果）；③ 所有降级状态必须有明确的"恢复时机"，不允许出现不可逆的卡死。

| 故障模式 | 触发与检测 | 处理路径（设计落点） | 恢复策略 | 用户可见反馈 |
| -------- | ---------- | -------------------- | -------- | ------------ |
| FM-01 本地存储不可用 | 写入/读取抛异常（隐私模式、配额满、用户禁用） | M10 的存储适配器捕获 → 置"只读模式" → 广播 `save:changed{saved:false}`（I-22） | 每次会话开始时探测一次可写性；变可写则恢复写入 | 顶部提示条"当前浏览器环境无法保存进度，关闭页面后可能丢失" |
| FM-02 死局 | 每次结算后 `isDeadlock` 为真（I-03） | 自动洗牌（I-04，不消耗步数）→ 广播 `deadlock:shuffled`；连续 5 次仍死局 → 重建棋盘并保持重建语义（FL-01/B5/B6） | 重建后 `shuffleCount` 归零，重新计数 | 提示"无可消除组合，已自动重排" |
| FM-03 排行榜网络中断/超时 | `fetch` 失败或 3s 超时（I-33/I-34） | 降级为本地模拟榜单（I-35），`source='local'` | 进入排行榜页时若在线则重新尝试远端；提供"重试"按钮 | 标注"本地模拟数据"+"网络不可用，排行榜暂不可用，单机游玩不受影响" |
| FM-04 排行榜服务端错误 | HTTP 5xx 或返回 code 5000 | 停止本次提交，置"待提交"标记 | 页面重试按钮；保持标记供下次进入榜单页时重试 | 提示"排行榜暂时不可用"，附"重试"按钮 |
| FM-05 昵称非法/含脚本片段 | 客户端预校验不通过；或服务端返回 1001 | 客户端拦截并拒绝提交（不发请求）；服务端二次校验拒绝 | 停留在设置页，用户修改后重新提交 | 提示"昵称仅支持 3–12 个中英文、数字或下划线" |
| FM-06 分数被篡改为越界值 | 提交值 > 2,150,000 或类型非法 | 客户端预校验拦截；服务端按 §6.3.1 校验序返回 1002 并丢弃该次提交 | 不影响本地进度；下次合法提交正常 | 提示"分数数据异常，本次成绩未提交" |
| FM-07 设备时间回拨/前拨 | `now < anchor` 或 `elapsed` 异常大 | M4 的 `restoreLives` 把 `elapsed` 钳为 0；锚点按"锚点 + 已恢复次数 × 15min"推进（I-17） | 锚点始终不被回拨；恢复次数与生命上限约束恢复量 | 生命值保持不变，不异常增加也不清零 |
| FM-08 动画推进被中断 | 兜底检查发现"动画超时未完成"（§3.5.4） | 强制完成动画、释放输入锁；完成动作以批次序号幂等 | 切回前台后可继续正常操作；动画批次不再回放 | 无额外提示（用户看到的是动画"很快结束"） |
| FM-09 音频上下文被挂起 | 创建/恢复 `AudioContext` 失败 | 静默降级：本次不播放，不抛错（I-30 内部处理） | 下一次用户交互时重试恢复；连续失败则本次会话放弃音频 | 无声音但不报错；用户点击后音效恢复（若恢复成功） |
| FM-10 存档版本不兼容/字段缺失 | 读存档时 `version` 旧、字段缺失或 JSON 不可解析 | 旧版本走迁移链；缺字段按默认值补齐；不可解析 → 备份到 `gemz_save_v1.corrupt.<时间戳>` 后重置（§5.3/B2/B3/E1） | 备份键保留原值，用户可导出留档（FR-13） | 补齐时无提示；重置时提示"存档已损坏，已备份并重置" |
| FM-11 同分玩家名次抖动 | 多名玩家同分且时间窗内多次查询 | 服务端以 `id` 自增序号为次序键（§7.4.1）+ 10 秒写入节流窗口（§6.3.2） | 无需恢复；排序键恒定，名次天然稳定 | 连续刷新名次顺序一致（TC-21） |
| FM-12 关卡配置数据缺失或非法 | 启动时逐条校验失败（§7.3.1） | 非法条目替换为该分段默认配置并写 `gemz_diag_config`；合法条目 < 30 时整体回落内置默认 | 无需用户操作；运维侧修正配置后随版本发布 | 合法条目 < 30 时提示"关卡数据异常"；个别条目被替换时不打扰用户 |
| FM-13 多标签页写入冲突 | 写前比对 `updatedAt` 发现外部写入；或收到 `storage` 事件 | 先按 FL-04 的逐字段规则合并再写；对局不中断（I-20/I-24） | 合并后两组进度都不丢失；单飞串行化避免递归冲突 | 提示"进度已从其他标签页更新" |
| FM-14 金币不足 | 购买/补满时余额 < 价格 | M4 返回 `ok=false` 与差额（I-16/I-18），不扣币、不改库存/生命 | 玩家可通过通关获取金币后重试 | 按钮置灰，提示"金币不足，还差 N 点" |

**错误码与用户可见文案汇总（与 §6 错误约定一致）：**

| 错误码 / 标记 | 来源 | 含义 | 客户端行为 | 文案（统一常量表） |
| ------------- | ---- | ---- | ---------- | ------------------ |
| `0` | HTTP-1/HTTP-2 | 成功 | 更新名次/展示榜单 | — |
| `1001` | HTTP-1 | 昵称非法 | 拒绝提交、停留设置页 | 昵称仅支持 3–12 个中英文、数字或下划线 |
| `1002` | HTTP-1 | 分数非法/越界 | 拒绝本次提交，不影响本地进度 | 分数数据异常，本次成绩未提交 |
| `5000` | HTTP-1/HTTP-2 | 服务端错误 | 停止本次提交，可重试 | 排行榜暂时不可用 |
| `'offline'` | 客户端（I-33） | 网络失败/超时 | 降级本地模拟榜单 | 网络不可用，排行榜暂不可用，单机游玩不受影响 |
| `'readonly'` | 客户端（I-22） | 存储不可用 | 进入只读模式 | 当前浏览器环境无法保存进度，关闭页面后可能丢失 |
| `'nan'`（`NaN` 标记） | 客户端（渲染层） | 数值异常 | 以 0 显示并记日志（防御性兜底） | — |

**故障处理的覆盖自检：** `01` 的 14 条故障模式在上表逐条有"触发与检测 / 处理路径 / 恢复策略 / 用户可见反馈"四要素，无缺项；其中 FM-11 的处理主要在服务端（§7.4），其余 13 条在前端有完整落点。每条故障模式的主处理路径均能对应到 §5 的某个流程小节（对照见 §5.8 的"覆盖故障模式"列）。

## 10. 设计决策与权衡

**承接需求：** 本章 12 项关键决策覆盖架构形态、渲染、数据、存储、协议与流程编排；每项给出备选方案、选择理由与被否决方案的否决理由。其中 **D-04 是修正项 K-03 对应的技术决策**（承载对实验一需求文档缺陷的修正），四项修正的汇总见 §13.2。

| 编号 | 决策 | 选择 | 备选方案 | 选择理由 | 被否决方案的理由 | 影响范围 |
| :--: | ---- | ---- | -------- | -------- | ---------------- | -------- |
| D-01 | 技术形态 | 单页应用 + 模块化 TypeScript，编译为**零运行时依赖**的静态资源（AC-A1~AC-A5） | ① 单文件 HTML（全部内联）② 引入 UI 框架（React/Vue）③ 构建工具链（Vite/Webpack） | 需求 NFR-09 要求前端为纯静态资源且"除构建产物外无运行时依赖"（检查单第 1 项）；游戏核心是 Canvas 绘制与固定循环，框架的组件模型与虚拟 DOM 在此无收益；无依赖也使 NFR-03 的体积预算（≤ 5MB）与 NFR-01 的首屏预算（≤ 5s）天然可达 | ① 单文件无法承载 12 个模块与 35 个接口，可维护性与可测试性归零，违背 NFR-10 的配置驱动思路；② 框架包体（≥ 30KB gzip）与学习/维护成本对单人课程项目是净负担，且违背"NFR-09 检查单第 1 项"；③ 打包器带来插件生态与版本管理成本，而本项目只需"TS → ES 模块 → 单包"的最小流水线 | 全部模块；§3 架构、§12.1 测试手段 |
| D-02 | 渲染方式 | **Canvas 2D** + 脏区域重绘 | ① DOM 网格（64 个元素）② WebGL | 消除/下落/补充是多元素同时位移与缩放的动画（FR-03、FR-25），Canvas 的绘制与补间控制粒度最细；冰层叠加、粒子、全屏闪白都在同一坐标系内完成；自绘图形天然满足 NFR-11（无外部素材） | ① DOM 方案在 64 格同时重排 + 粒子时会触发大量布局与重绘，FR-25 的时长上限与 NFR-02 的 30 FPS 目标更难稳定达成，且"动画期间的输入队列"需要在 DOM 事件里再做一层拦截；② WebGL 需要着色器与上下文管理，对 2D 简单图形的正确性没有收益，属过度设计 | M6；§8.5 布局、§9.1 帧率预算 |
| D-03 | 棋盘与元素规模 | 固定 8×8、5 色（BR-01） | 可变棋盘尺寸（随关卡变化） | BR-01 是需求基线给定的常量；固定尺寸使死局检测的枚举规模恒定（112 组交换）、代理求解器的 200 局模拟数据与星级标定分布（V-13/V-17）可直接复用；移动端 8 列宽度在 360px 视口下每格 ≥ 40px，满足触控命中 | 可变尺寸会推翻既有全部数值标定（步数、目标分、星级阈值都依赖棋盘规模），且没有对应的需求；属"为设计而设计" | M1、DS-2；§7.3 全表 |

### 13.3 需求语义的解释性说明（不构成变更）
