# 开发路线图（P0–P8）

本路线图把设计文档的模块映射为 9 个阶段。每个阶段结束都应有一个可运行的增量、一组提交、一个 PR 和一个 tag（或 release 候选）。

## 3. 依赖关系

```text
P0 ──┬── P1 ──┐
     └── P2 ──┴── P3 ──┬── P4 ──┐
                        └── P5 ──┴── P6 ── P7 ── P8
```

- P1 与 P2 可并行；P4 与 P5 可并行。
- P6 依赖 P3、P4、P5 的接口稳定。
- P7 从 P2 开始持续补测试，不等所有功能完成。
- P8 从 P6 开始写文档，不等最后一天。

## 4. 提交与发布节奏

- 每个阶段拆成 **3–8 个提交**，每个提交只做一件事；每个提交应能通过 `npm test`。
- 功能分支从 `develop` 切出，PR 合并到 `develop`；阶段结束 `develop` → `main` 的 release PR。
- Tag 规划：
  - `v0.1.0`：仓库骨架与协作规范（P0 前）；
  - `v0.2.0`：核心玩法可玩（P0–P3 + 最小界面）；
  - `v0.3.0`：功能完整（P4–P6）；
  - `v1.0.0`：测试与交付完成（P7–P8）。
- 每个 release 更新 `CHANGELOG.md`，写清新增、修复、已知限制。

## 5. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 三人时间不同步 | 某阶段阻塞 | 每个模块接口先定契约；用 mock 并行开发 |
| UI 工作量大 | P5 拖延 P6 | 先做最小可玩界面，再补动效/无障碍 |
| 排行榜后端不存在 | 无法真实联调 | 按设计只做客户端 + mock + 降级；不虚构服务端能力 |
| 旧原型诱惑 | 直接复制导致历史失真 | 旧原型只作参考；新实现按基线重写，保留小提交 |
| 最后集中提交 | 过程分低 | 每周检查 contributors 与提交时间分布；提前拆 issue |
